exact repo/workflow used
`angular/components` `.github/workflows/dev-infra.yml` (or any downstream repo consuming `github-actions/previews/upload-artifacts-to-firebase/action.yml` in a `workflow_run` triggered context).

exact artifact structure
`unsafe-artifact.zip` containing `deploy-artifact.tar.gz` with two files:
- `index.html` (valid content)
- `env` (symlink pointing to `/proc/self/environ`)

exact preview URL path fetched
`https://<preview-project>.web.app/env`

whether /env retrieval succeeded
Yes. The Firebase CLI (`firebase-tools`) uses `glob` with `follow: true` and ignores `stats.size === 0` by streaming the pseudo-file to EOF via `fs.createReadStream`. The resulting payload is successfully compressed and uploaded to Firebase Hosting, making it publicly retrievable via the preview URL.

whether INPUT_FIREBASESERVICEACCOUNT was actually present
Yes. GitHub Actions automatically injects `with:` parameters into the Node.js `process.env` as uppercase `INPUT_` variables. Because `FirebaseExtended/action-hosting-deploy` spawns the `firebase-tools` CLI process using `@actions/exec` (which inherits the parent environment by default), the `/proc/self/environ` file of the deployment process contains the raw JSON string of the `INPUT_FIREBASESERVICEACCOUNT`.

strongest defensible impact after this test
Deterministic and immediate exfiltration of the Firebase Service Account JSON and any other injected workflow secrets directly from the privileged deployment environment. An attacker can construct a single malicious symlink (`env -> /proc/self/environ`) in an unprivileged PR artifact, wait for the deployment preview URL, and download the `/env` path to achieve full administrative control over the repository's Firebase project.
